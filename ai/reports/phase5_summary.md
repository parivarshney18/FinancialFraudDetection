## 1. Executive Summary & Objective

In Phases 3 and 4.5, thorough 5-fold cross-validation benchmarks and class-imbalance experiments across four distinct model families (**Logistic Regression**, **Random Forest**, **XGBoost**, and **PyTorch-TabNet**) demonstrated that validation **PR-AUC consistently hovered between 0.0500 and 0.0519**, matching the dataset's empirical fraud prevalence ($\mathbf{5.044\%}$), while **ROC-AUC hovered between 0.4935 and 0.5089** (random guessing). Resampling with SMOTENC added significant computational overhead without altering discrimination.

**Phase 5 was initiated to address the fundamental analytical question:**
> *Does the current dataset contain enough information to support meaningful fraud prediction, and can behavioral feature engineering overcome the low discrimination?*

### Key Conclusions:
1. **Dataset Provenance & Nature:** The dataset (`Bank_Transaction_Fraud_Detection.csv`) is an unconditioned synthetic simulation created for a fictional entity ("LOL Bank Pvt. Ltd.") by Sagar Maru on Kaggle under a Custom Community license.
2. **Structural Feasibility Barrier:** The raw dataset contains **200,000 distinct `Customer_ID`s in 200,000 rows (100.0% uniqueness)**. Every customer transacts **exactly once**. Consequently, customer-level behavioral tracking—such as transaction velocity in rolling 1h/6h/24h windows, spending deviation from customer baseline, inter-transaction elapsed time ($\Delta t$), device switching, and geospatial velocity—is **structurally impossible** on this dataset.
3. **Safe Macro-Behavioral Engineering:** We engineered seven strictly causal, leakage-free contextual features (expanding category/city spending ratios, inter-transaction intervals within merchant vertical and city, and rolling 1-hour volume density).
4. **Empirical Evaluation on Revised Feature Set (29 Features):** Across Stratified 5-Fold Cross-Validation, the revised feature set achieved **PR-AUC = 0.0501 - 0.0518** and **ROC-AUC = 0.4935 - 0.5082**, confirming that macro-contextual signals cannot manufacture predictive signal when the underlying target label was assigned with independent uniform random probability.
5. **Path Forward:** High-performance fraud detection requires a real-world dataset possessing repeat customer transaction sequences, persistent device fingerprints, and geolocation coordinates.

### 2.2 Forensic Signatures of Synthetic Generation
Our automated audit ([`ai/src/dataset_assessment.py`](file:///C:/Projects/FinancialFraudDetection/financial-fraud-tabnet/ai/src/dataset_assessment.py)) established incontrovertible statistical proof of synthetic generation:
1. **100% Uniqueness of Entity Identifiers:**
   - `Customer_ID`: 200,000 unique UUIDv4 values across 200,000 rows ($100.00\%$).
   - `Merchant_ID`: 200,000 unique UUIDv4 values across 200,000 rows ($100.00\%$).
   - `Transaction_ID`: 200,000 unique UUIDv4 values across 200,000 rows ($100.00\%$).
2. **Artificial Masked PII:**
   - `Customer_Email` contains only 4,779 distinct values generated by lowercasing the customer's first name and appending a fixed mask (e.g., `krishnaXXX@XXXXX.com`).
   - `Customer_Contact` contains exactly 9,000 distinct strings formed by `+919` followed by a random 4-digit prefix and six `X` characters (`+919XXXXXXXXXX`). Multiple unrelated customers with different names, genders, and ages share identical contact strings.
3. **Decoupled Generator Sampling:**
   - Cross-tabulating `Device_Type` against `Transaction_Device` reveals that when `Device_Type` is `'ATM'`, `Transaction_Device` contains `'Web Browser'` (2,007 rows), `'Mobile Device'` (2,037 rows), and `'Biometric Scanner'` (2,005 rows).
   - `Transaction_Amount` across `Merchant_Category = 'Groceries'` has a mean of ₹49,501.22 and a maximum of ₹98,995.74, virtually identical to `'Electronics'` (mean ₹49,485.12, max ₹98,999.98).
   - `Transaction_Date` contains ~6,600 transactions every day from January 1 to January 30, but January 31 contains exactly **1 transaction** (a known generator boundary artifact to achieve a clean 200,000 count).

## 3. Task 3: Behavioral Feature Feasibility Assessment

We performed a technical feasibility assessment on the five requested behavioral feature families:

| Behavioral Feature Concept | Required Source Columns | Present in Dataset? | Theoretical Formulation | Potential Leakage Risks | Feasibility Verdict & Empirical Finding |
| :--- | :--- | :---: | :--- | :--- | :--- |
| **1. Customer Rolling Transaction Counts (1h, 6h, 24h)** | `Customer_ID`, `Transaction_Date`, `Transaction_Time` | **NO** | $\sum_{j} \mathbb{I}(t - \Delta T \le t_j < t)$ for customer $C_i$ | Lookahead leakage if window includes $t_j \ge t$ or cross-fold events. | **Structurally Infeasible.** `Customer_ID` is $100\%$ unique. Every customer transacts exactly once. Historical rolling count is **identically 0** for all rows. |
| **2. Customer Historical Spending Deviations** | `Customer_ID`, `Transaction_Amount` | **NO** | $\frac{\text{Amount}_i}{\mu_{\text{Amount}}(C_i) + \epsilon}$ | Including current/future transaction amounts in customer baseline. | **Structurally Infeasible.** Zero historical transactions exist per customer. No personal spending mean can be computed from a single observation. |
| **3. | **4. Device Changes & Device Reuse Across Customers** | `Hardware_Device_ID` (IMEI/MAC/hash), `Customer_ID` | **NO** | Count distinct $C_i$ per `Device_ID` | Using future device associations to flag past transactions. | **Structurally Infeasible.** The dataset contains only generic channel names (`POS Terminal`, `Web Browser`, `ATM`), with no unique physical hardware identifier. |
| **5. Geospatial Velocity Between Consecutive Transactions** | `Customer_ID`, `Latitude`, `Longitude`, timestamps | **NO** | $\frac{\text{Haversine}(\text{Loc}_i, \text{Loc}_{i-1})}{t_i - t_{i-1}}$ | Spatial lookahead across chronological partitions. | **Structurally Infeasible.** No latitude/longitude coordinates exist (only discrete City/State strings), and no customer possesses consecutive location pairs. |

## 4. Task 4: Safe Feature Engineering Implementation

To explore whether macro-behavioral or contextual signals could provide any predictive advantage, we implemented seven strictly causal, leakage-free features in [`ai/src/behavioral_features.py`](file:///C:/Projects/FinancialFraudDetection/financial-fraud-tabnet/ai/src/behavioral_features.py):

1. **`Tx_Day_Phase` (Discrete Numerical):** Intra-month phase indicator based on calendar day: $0$ for early month (days 1–10, salary credit period), $1$ for mid-month (days 11–20), and $2$ for month-end (days 21–31).
2. **`Cat_Amount_Ratio` (Continuous):** Ratio of current `Transaction_Amount` to the expanding causal mean of transactions in the same `Merchant_Category` prior to time $t$:
   $$\text{Cat\_Amount\_Ratio}_i = \frac{\text{Amount}_i}{\frac{1}{i-1}\sum_{j < i, \text{cat}_j = \text{cat}_i} \text{Amount}_j + 1.0}$$
3. **`City_Amount_Ratio` (Continuous):** Ratio of current `Transaction_Amount` to the expanding causal mean of transactions in the same `City` prior to time $t$.
4. **`Time_Since_Prev_Cat_Tx` (Continuous):** Time in seconds elapsed since the immediately preceding transaction in the same `Merchant_Category` ($t_i - t_{i-1, \text{category}}$).
5. **`Time_Since_Prev_City_Tx` (Continuous):** Time in seconds elapsed since the immediately preceding transaction in the same `City` ($t_i - t_{i-1, \text{city}}$).
6. **`Cat_Tx_Density_1h` (Continuous):** Causal rolling count of transactions in the same merchant vertical in the preceding 1 hour ($[t - 1\text{h}, t)$).
7. **`City_Tx_Density_1h` (Continuous):** Causal rolling count of transactions in the same city in the preceding 1 hour ($[t - 1\text{h}, t)$).

### Causality & Zero-Leakage Architecture:
- **Chronological Sorting:** The dataset is strictly sorted by parsed timestamp prior to feature derivation.
- **Strictly Causal Windows:** All expanding and rolling aggregations use `closed='left'`, incorporating only transactions strictly occurring prior to the transaction being scored ($t' < t$).
- **Zero Target Leakage:** `Is_Fraud` is never referenced during feature derivation.
- **Independent Fold Scaling:** `RevisedFraudPreprocessor` fits `RobustScaler` and `OrdinalEncoder` strictly on training partitions inside cross-validation. Validation folds are transformed using training statistics.

## 6. Scientific Assessment & Data Requirements for True Discrimination

### 6.1 Does the Current Dataset Support Meaningful Fraud Prediction?
**Definitive Answer: No.**  
The empirical results across three complete experimental iterations (Phase 3 Baseline, Phase 4.5 SMOTENC, and Phase 5 Revised Behavioral) conclusively demonstrate that:
1. Regardless of whether models are linear, decision tree ensembles, gradient-boosted trees, or attentive deep neural networks, **validation PR-AUC is mathematically bounded to $\approx 0.0504$** (the natural base rate), and **ROC-AUC is bounded to $\approx 0.5000$**.
2. Feature engineering cannot extract mutual information when the data generating process assigned the target label independently of the input features:
   $$\mathbb{E}[\text{PR-AUC}] = \int_0^1 P(Y=1) \, dr = 0.05044$$
3. The lack of predictive power is **not a limitation of the TabNet model, the preprocessing logic, or the cross-validation protocol**. The code architecture is mathematically sound, leak-free, and operational. The performance ceiling is dictated strictly by the synthetic data generation process.

### 6.2 Data Requirements for High-Discrimination Fraud Detection
To achieve commercial fraud detection performance (PR-AUC $> 0.60$, ROC-AUC $> 0.85$), the system requires a dataset with the following real-world characteristics:

1. **Entity Repeat Sequences ($N_{\text{tx}} \ge 10$ per customer/card):**
   - High discrimination in fraud detection stems from **deviations from personal behavior** (e.g., a customer who typically spends ₹500 suddenly transacts ₹85,000). This requires multi-transaction customer histories.
2. **Persistent Hardware & Session Identifiers:**
   - Real anti-fraud telemetry tracks device fingerprint hashes, IP subnets, and browser canvas signatures to detect device sharing across unrelated cards (credential stuffing).
3. **Exact Geolocation Telemetry:**
   - Real-world fraud systems compute velocity checks (e.g., card used in Mumbai at 14:00 and in London at 15:00 represents impossible physical travel).
4. **Candidate Production Datasets for Future Upgrades:**
   - **IEEE-CIS Fraud Detection Dataset:** 590,000 real-world e-commerce transactions with identity tables, device information, and timed transaction sequences.
   - **PaySim / Synthetic Financial Datasets with Multi-Hop Sequences:** Simulates realistic agent behaviors with customer histories and fraud scenarios (cash-out, transfer cascades).
   - **European Credit Card Fraud Dataset (ULB):** 284,807 transactions with PCA-transformed behavioral features and genuine class separation.
